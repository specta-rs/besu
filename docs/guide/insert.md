# Inserting data

An insert starts from the table handle and takes either one row or many:

```rust
let created: Vec<User> = db
    .insert(users)
    .value(users.insert("oscar@example.com", "Oscar", 21))
    .returning(users)
    .await?;
```

`users.insert(..)` is not a builder method; it is generated by `#[derive(Table)]` and returns
the table's insert struct. Its arguments are exactly the columns the database cannot fill in
for you, in declaration order.

## The generated insert struct

For this table:

```rust
#[derive(Table)]
#[besu(table = "users")]
pub struct User {
    #[besu(primary_key, auto_increment)]
    pub id: i64,
    #[besu(unique)]
    pub email: String,
    pub name: String,
    pub age: i32,
    pub bio: Option<String>,
}
```

the macro generates a struct with one `Set<T>` field per column and a constructor with three
arguments:

```rust
pub struct UserInsert {
    pub id: Set<i64>,
    pub email: Set<String>,
    pub name: Set<String>,
    pub age: Set<i32>,
    pub bio: Set<String>,
}

impl UserTable {
    pub fn insert(
        email: impl Into<String>,
        name: impl Into<String>,
        age: impl Into<i32>,
    ) -> UserInsert { /* ... */ }
}
```

The requirement rule is: **not nullable, not auto-incrementing and no default**. Everything
else starts as `Set::Unset` and is left to the database. Required arguments are
`impl Into<T>`, so `users.insert("a@example.com", "Oscar", 21)` works without `.into()`
noise; a `String` or an `i32` works too.

Every column also gets a setter, so you can fill in the optional ones after construction:

```rust
users.insert("oscar@example.com", "Oscar", 21)
    .bio("Rust")
```

```rust
users.insert("oscar@example.com", "Oscar", 21)
    .bio(None::<String>)
```

The two are different statements. The first writes `'Rust'`; the second writes `NULL`. Not
calling the setter at all omits the column, so the database default applies.

## `Set` and the three meanings of `None`

`Set<T>` is the type that makes "not provided" distinguishable from "provided as `NULL`":

| State | `INSERT` behaviour |
| --- | --- |
| `Set::Unset` | The column is omitted, so the database default (or `NULL` for a nullable column with no default) applies |
| `Set::Null` | The column is written as an explicit `NULL` |
| `Set::Value(v)` | The column is written with the bound value `v` |

The conversions decide which one you get:

- `T` becomes `Set::Value(T)`.
- `&str` becomes `Set::Value(String)` for a `Set<String>` field.
- `Option<T>` becomes `Set::Value` for `Some` and `Set::Null` for `None`.
- `Set<T>` is used as-is.

`Set::is_set()` reports whether `NULL` or a value was provided (that is, anything except
`Unset`), and `Set::to_value()` converts to `Option<Value>` for the query builder.

This distinction is why a nullable column with a `DEFAULT` behaves correctly: omitting it
lets the default run, while passing `None` overrides the default with `NULL`.

## Many rows at once

`values` takes any iterator of insert structs and emits a single multi-row `INSERT`:

```rust
db.insert(posts)
    .values([
        posts.insert("Hello, world", oscar.id),
        posts.insert("A second post", oscar.id),
    ])
    .await?;
```

The column list is the union of the columns any row provides. If one row provides a column
and another does not, the gap is filled with the `DEFAULT` keyword — but not every dialect
supports `DEFAULT` inside `VALUES`. SQLite does not, so a ragged bulk insert on SQLite is a
build error rather than a wrong row:

```text
unsupported: `sqlite` does not support `DEFAULT` inside `VALUES`, and this bulk insert
provides `bio` in some rows but not others
```

Give every row the same set of provided columns when targeting SQLite. MySQL does support
`DEFAULT` in `VALUES`, so the ragged form works there.

An insert with no rows is also a build error: `insert` requires at least one `value` or
`values`.

## `RETURNING`

Without `returning`, awaiting an insert resolves to the driver's output — for SQLite a
`SqliteQueryResult` with `rows_affected()`. With it, the query returns the inserted rows:

```rust
let rows: Vec<User> = db
    .insert(users)
    .value(users.insert("a@example.com", "Alice", 30))
    .returning(users)
    .await?;
```

`returning` takes the same selections as `pick`:

```rust
let ids: Vec<i64> = db.insert(users)
    .value(users.insert("a@example.com", "Alice", 30))
    .returning(users.id)
    .await?;

let names: Vec<(i64, String)> = db.insert(users)
    .value(users.insert("b@example.com", "Bob", 20))
    .returning((users.id, users.name))
    .await?;
```

`returning(users)` is the whole row, including generated columns. It is the reliable way to
learn the `id` an auto-increment column produced.

`RETURNING` is dialect-dependent. PostgreSQL and SQLite support it; MySQL does not. Because
the check is a capability flag rather than a type, a MySQL insert with `returning` compiles and
then fails while building the SQL with `unsupported: \`mysql\` does not support \`RETURNING\``.
On MySQL, insert and then select the row back.

## Upserts

`on_conflict` starts an upsert. It takes a column or a tuple of up to four columns as the
conflict target:

```rust
db.insert(users)
    .value(users.insert("oscar@example.com", "Oscar", 22))
    .on_conflict(users.email)
    .do_update(users.age, 22)
    .await?;
```

```sql
INSERT INTO "users" ("email", "name", "age") VALUES (?, ?, ?)
ON CONFLICT ("email") DO UPDATE SET "age" = ?
```

`.do_nothing()` is the other action:

```rust
db.insert(users)
    .value(users.insert("oscar@example.com", "Oscar", 22))
    .on_conflict(users.email)
    .do_nothing()
    .await?;
```

```sql
... ON CONFLICT ("email") DO NOTHING
```

`do_update` may be called repeatedly to set several columns. When the unique key is composite,
the target may be a tuple of up to four columns:

```rust
.on_conflict((users.email, users.team_id))
```

That requires a matching composite unique constraint in the database; Besu checks the columns
exist, not that the constraint does.

MySQL spells this differently, and the query builder adapts:

```sql
INSERT INTO `users` (...) VALUES (...)
ON DUPLICATE KEY UPDATE `age` = ?
```

MySQL has no target on its upsert — the unique key decides — so the tuple passed to
`on_conflict` is ignored there. MySQL also has no `ON CONFLICT DO NOTHING` that is safe to
emulate, so `do_nothing` on MySQL is an `unsupported` error; use `do_update` instead.

## Inserting a model

`UserInsert` implements `From<User>`, so an existing row can be inserted again:

```rust
let copy: UserInsert = user.clone().into();
db.insert(users).value(copy).await?;
```

The conversion follows the `Set` rules: an auto-increment column becomes `Unset`, a nullable
column becomes `Value`/`Null` from its `Option`, and a non-null column becomes `Value`. That
means a `None` in the model is written as `NULL`, not left to a default.

## Generated SQL

```rust
let sql = db.insert(users)
    .value(users.insert("oscar@example.com", "Oscar", 21))
    .to_sql()?;

assert_eq!(
    sql.sql(),
    r#"INSERT INTO "users" ("email", "name", "age") VALUES (?, ?, ?)"#
);
```

With `returning(users)`, the same statement ends in
`RETURNING "users"."id", "users"."email", ...`.

## What is checked

| Mistake | When it fails |
| --- | --- |
| Forgetting a required column | Compile error: `users.insert(..)` has the wrong arity |
| Passing the wrong type for a required column | Compile error |
| Setting a column to a value of the wrong type | Compile error at the setter |
| Referencing a column the table does not have | Compile error: no such field |
| Inserting zero rows | Runtime build error |
| More parameters than the dialect allows | Runtime build error with a suggested batch size |
| Ragged bulk insert on a dialect without `DEFAULT` in `VALUES` | Runtime build error |
| `RETURNING` on a dialect without it | Runtime build error |
| `ON CONFLICT` with no target on PostgreSQL or SQLite | Runtime build error |
| `do_nothing` on MySQL | Runtime build error |

## Gotchas

- **`do_update` without `on_conflict` is a build error on PostgreSQL and SQLite.** It emits
  ``ON CONFLICT needs a target column; call `.on_conflict(column)` first``. MySQL ignores the
  target, so the chain happens to work there, but call `on_conflict` first for a statement
  that is valid everywhere.
- **Do not write `.into()` on insert arguments.** The parameter is `impl Into<String>` (or
  `impl Into<i32>`), so the target type is not concrete and the compiler sees several
  `From<&str>` impls in scope. Pass the literal or a value of the exact type.
- **Bulk inserts have a parameter ceiling.** Every value is a bound parameter, and each
  dialect has a limit (`SQLITE_MAX_VARIABLE_NUMBER` is 32,766 by default; the others default
  to 65,535). An insert that exceeds it is a build error that reports the largest batch size
  that fits; split the iterator into batches.
- **A nullable field is optional, not required-and-nullable.** `users.insert(..)` does not
  ask for `bio`; use the setter to say `NULL` explicitly.
- **A column with a default is optional even when it is `NOT NULL`.** `posts.insert(..)` does
  not ask for `published` when it has `#[besu(default = false)]`.
- **Bulk inserts on SQLite must be rectangular.** Every row must provide the same columns, or
  the build fails. Insert in separate statements if you need holes.
- **`FROM` a model writes `NULL` for `None`.** It does not reproduce the "column omitted" case.
- **The auto-increment setter exists.** You can call `.id(42)`, but whether the database
  accepts an explicit value depends on the database and its sequence state.
- **Upsert targets must match a real unique constraint.** Besu checks that the columns exist,
  not that the database has a unique index over them; a mismatch is a database error.
